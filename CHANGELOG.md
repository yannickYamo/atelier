# Changelog

## [Unreleased]

Atelier learns how you write from the pieces you would sign, writes new pieces that way, and reads each one for anything made up or copied before you see it.

- `atelier new` builds the check from your finished pieces, with or without a note of your own rules, and shows every rule for approval before it binds.
- `atelier verify` checks any text for invented specifics, passages copied from your examples and broken rules; as a Claude Code hook it blocks the break and hands the agent the reason.
- `atelier setup` lets the agents in a project call it through an MCP server, for Claude Code and Codex.
- It also writes to the standard: `atelier run`, then `atelier fix` in your own words.
- A skill built from your pieces now writes from them: your pieces of the kind asked for, whole, with your material, the task and your own stated rules, then one review against the same. `atelier keep` keeps the piece you published, so the next runs write from it and learn from each sentence you changed. `--pipeline legacy` keeps the compiled path.
- A skill built from one example writes from it, and a request that asks for only the figures given ("use only these figures") is written the same way, with every figure held to what you gave: one you did not give is rewritten, and if it stays the piece is blocked. An option of the compiled path typed as `--drafts=3` takes that path, as `--drafts 3` always did.
- A skill with your method shows it to the writer whole. Before the draft, an editor asks the open decisions that would change this piece's argument most (at most three, read from your request, material, method and the kind of work); where none is open, the one idea, the reader, their pain, the proof and the next step are asked wherever nothing you gave states them. Only your answers reach the writer, and a run nobody answers is written as before.
- A step such as "three paragraphs per section" is counted as paragraphs in every section (`LENGTH:unit=PARAGRAPHS,min=3,max=3,in=each`); it was read as sentences per paragraph and flagged a piece written to it. Each of your rules is said under the piece: held, not held, found by a check not yet qualified, or yours to judge.
- Rebuilding a skill reads its rules' checks again when the check reader has changed since they were read, so a skill built before the paragraph fix gets it on its next `atelier new`, in that one command: a build that closes a new version records itself as the reason (`--reason` gives another). A count in words in the piece ("five or six teams") is held to your request and notes only: the same number in one of your rules no longer passes it. A range ("five or six pieces") or more than ten of a thing ("fifty pieces") is a count, and a moment the notes never gave ("this afternoon", "last week", "two months ago") is listed beside the piece for you to check.
- A skill whose release you set with `atelier fidelity --set` to something only the compiled path runs (`mode=deep`, the voice pass, sampled selection, local context, the subject reader, served moves) now runs it on a plain run; it ran plain before. The check for names carried over from your examples reads every piece the writer can be shown, the kept ones included. A skill built again from a changed method says which version it supersedes, and a skill whose rule checks an earlier check reader read says so on every run and in `atelier status --skill` until it is built again.
- A test builds a skill, runs it the default way with the store traced (`ATELIER_TRACE_STORE`), and holds every file and voice field the build wrote to a table of who reads it: a new artifact with no reader, or a reader that no longer reads, fails it.
- How you write is read on every piece: the habits the build reads from your pieces that you show always or often, and the steps of your method no check reads, each said under the piece as held (with the piece's words), not held or not read. It was built and read by nothing on a plain run. Report only; `--style-review` tells the self-review what the first draft does not hold, for a comparison before it is the default; `--no-style` turns it off. `atelier report` shows it, with what each piece was written from. A rule whose judgement reader your labels qualified to hold it takes the compiled path, where that reader runs; `--pipeline direct` always runs the direct writer.
- The skill installed for a host (Claude Code or Codex), and `atelier export`, give the host your pieces, your method and your rules, as `atelier run` does: the description of how you sound and the moves read off your pieces are no longer served there as instructions (`atelier export --whole` keeps them). A skill built with no method has the steps read off its pieces read on every piece with your habits. What each step asks the writer to decide is read on the compiled path's first run that needs it, not paid for at every build. A release set to more than two drafts runs on the compiled path, which writes them. With `--style-review` the piece is read again after the review, and one line says how many of the misses the review fixed.
- A plain run now does what only the compiled path did: a fact carried from one of your pieces into this one is rewritten to what you gave, the evaluation says how typical of you the piece is, each grammar slip is named beside it and a `--fix-grammar` change is said, the method line says what the piece carries out, and a rule no count checks says the judgement reader did not run. A grammar rule whose checker was switched off reads "not checked". Which lines of your method note are steps (a title, a list of inputs) is read by the model where one is set up. Every flag a command reads is in its help, and a test holds it there.
- Which of your habits are read on the piece is decided by how many of your pieces show each one, where the build counted them, instead of the reading's own word for how often. `atelier models` says how to choose the model a command uses. A test holds every model reading to the place it runs and every flag the code reads to the declared ones.
- The editor's questions are the same on the same request and notes, and an answer belongs to the request it was given for: asked once, it reaches the writer on the next run of that request; another request is asked afresh.
- Small invented details are listed: a range in words ("eleven or twelve teams"), a count in words where a model reads the claims, and a detail the reader named in a line otherwise copied from your notes.
- The review after the first draft fixes only what you would not write, or what your material does not give, and leaves the rest as it was. On the default path the claim check reads each piece once: it lists and never cuts there, so a second read added cost and nothing else.
- The text a run hands back is clean: a specific to check is listed beside it, never marked in it (`--mark-unverified` marks it in place, for a draft you will read, not publish). A sentence your notes hold is never listed as not given, and where a reader found part of a sentence untraced, that part is named.
- `atelier fix` reaches a table cell: every table row is one unit it can change, and a row comes back as one row with the same cells. A run whose required rule failed but that your consequence table still sends out says so in one line.
- A banned word inside a link address, or one your request itself uses, is not a break of the list; a word your rule allows a number of times (`mcp<=1`) is on the list from its next use.
- A run never stops or leaves a gap for what it was not given: it decides on what you gave, and lists beside the piece what it decided, what it was not given and what to add (`inferred`). The piece itself never talks about its notes or its gaps.
