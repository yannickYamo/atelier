## Summary

This change adds role and permission helpers for the admin console, deriving permissions from a flat `ROLE_GRANTS` table keyed by role name. It exposes `rolesOf`, `permissionsOf`, `hasRole`, `hasPermission`, `isAdmin`, and an `assertCan` guard that throws a 403-tagged error for route handlers. The module is self-contained and has no external dependencies.

## Must fix

- **src/perm/roles.js:151** — The admin check uses `||` where `&&` is required. As written, any active user is treated as an admin regardless of role, and `assertCan` returns early for them, granting every permission including `manage_users`. This is a privilege escalation affecting every route behind the guard.
- **src/perm/roles.js:136** — `hasRole` compares the caller's `role` argument against roles that `rolesOf` has trimmed and lowercased, so a mixed-case or padded argument silently fails to match. Normalize the argument the same way before comparing.
- **src/perm/roles.js:128** — Role lookup indexes `ROLE_GRANTS` directly with a user-supplied string, so inherited keys such as `constructor` resolve to a truthy non-array and `grants.forEach` throws. Use `Object.prototype.hasOwnProperty.call` or a `Map`.

## Suggestions

- No tests accompany this behaviour. Add a unit test for `isAdmin` covering an active non-admin user, which would have caught the line 151 defect, plus a test that `assertCan` throws with `status === 403` for a viewer requesting `write`.
- `ROLE_GRANTS` is exported by reference and is mutable; callers can rewrite the grant table at runtime. Consider `Object.freeze` on the table and its arrays.
- `permissionsOf` rebuilds and sorts a full array on every `hasPermission` call. A `Set` return, or a membership check that short-circuits, would avoid the allocation on hot paths.
