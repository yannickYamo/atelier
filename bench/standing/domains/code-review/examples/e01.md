## Summary

This change adds a refund module that validates order state, converts a currency amount to cents, issues a credit through the payment gateway, and appends the refund to the order's history. It marks the order as `refunded` once the accumulated refunds equal the order total. The helper functions `refundedCents` and `toCents` are exported alongside `refundOrder`.

## Must fix

- **src/orders/refund.js:56** — The refund amount is never checked against what was actually paid or against prior refunds. A caller can refund more than `order.totalCents`, or refund repeatedly, and the gateway will be charged each time; compare `amountCents + refundedCents(order)` to `order.totalCents` before calling `createCredit`.
- **src/orders/refund.js:74** — The equality check `refundedCents(order) === order.totalCents` silently leaves an over-refunded order in its old status. Use `>=` so the state is correct even if totals drift.
- **src/orders/refund.js:61** — `createCredit` succeeds before `saveOrder` is attempted, so a failure at line 76 loses the refund record while the customer has been credited. Persist an intent first, or reconcile on failure.

## Suggestions

- Add tests for `refundOrder`: a partial refund, a full refund that flips status to `refunded`, an over-refund that is rejected, and a non-refundable status. None of this new behaviour is currently covered.
- `toCents` accepts `Infinity`; `Number.isFinite` would be a stricter guard than `Number.isNaN`.
- Line 71 stores `reason` unnormalized while line 65 defaults it to `customer_request`; store the same resolved value in both places.
