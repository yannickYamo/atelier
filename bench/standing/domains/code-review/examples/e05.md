## Summary

This change adds an in-memory `RateLimiter` class that tracks request counts per key within a fixed window. Consumption is serialized behind a promise-chain mutex, and helpers are provided to refund slots, sweep expired buckets, and reset a key. The class and its defaults are exported from the module.

## Must fix

- **src/rate/limiter.js:109** — `release` performs a read-modify-write of `bucket.count` outside `withLock`, contradicting the class comment that all counter access is guarded. A refund racing a `consume` can lose an update and let a key exceed `max`.
- **src/rate/limiter.js:107** — `release` also reads the bucket map directly instead of going through the lock, so it can decrement a bucket that `consume` is concurrently replacing after a window rollover, refunding a slot into the wrong window.
- **src/rate/limiter.js:73** — `this.lock.then(fn, fn)` runs `fn` on both settle paths, so a rejection from the previous critical section still invokes the next one with the error as its argument; use `this.lock.then(fn)` on a lock chain that never rejects.

## Suggestions

- `sweep` iterates and mutates `this.buckets` without the lock; consider routing it through `withLock` for consistency even though `Map` iteration tolerates deletion.
- `err.retryAfter` can be computed as a negative value if `now` drifts past the window end; clamp it to zero.
- No tests accompany this behaviour. Add a test asserting that a `consume` at the limit concurrent with a `release` for the same key leaves `count` consistent, plus a test for window rollover in `bucketFor`.
