## Summary

This change adds pagination helpers for the search API, translating `page` and `per_page` query parameters into offset/limit windows. It includes defensive coercion of raw query values via `_as_int`, and a `paginate` function that wraps a result set with navigation metadata such as `has_next` and `has_prev`.

## Must fix

- **src/search/paging.py:94** — `per_page` is taken straight from the request with no upper bound, so a client can send `per_page=1000000` and force an unbounded database read. Clamp the value to a `MAX_PAGE_SIZE` constant before returning it.
- **src/search/paging.py:104** — The offset is computed as `(page - 1) * size` with no ceiling on `page`, so a large page number produces a huge offset that most databases scan through expensively. Cap the offset or reject pages beyond `total_pages`.
- **src/search/paging.py:111** — `total_pages` divides by `page_size` without guarding against zero, so any caller passing `page_size=0` directly raises `ZeroDivisionError` rather than returning a sensible result.

## Suggestions

- `_as_int` catches `TypeError` alongside `ValueError`, but `str(raw)` has already removed the `TypeError` path; dropping it would make the intent clearer.
- `resolve_page_size` silently rewrites an out-of-range size to the default. Consider returning a 400 instead, so clients learn their parameter was ignored.
- No tests accompany these helpers. Add cases covering `build_window` for the first and later pages, `total_pages` with a remainder and with zero rows, and `resolve_page_size` rejecting an oversized `per_page` once the clamp is in place.
